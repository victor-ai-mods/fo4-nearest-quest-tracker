# Nearest Quest Tracker (NQT) — план разработки

Работа идёт в отдельных сессиях, по одному этапу или подэтапу за сессию.
**В начале каждой сессии:** прочитать этот файл (раздел «Статус» и нужный этап), затем
`..\FALLOUT4_MOD_DEVELOPMENT_GUIDE.md` (разделы 1 и 2). Другие этапы заново не разбирать.
**В конце сессии:** обновить «Статус» и «Решения и находки», чтобы следующая сессия
не выводила их заново, и дописать сценарии новой функции в «Чеклист полевого теста»
(тесты в игре — только минимальные, см. «Порядок тестирования»).

Префикс форм и скриптов: `NQT`. Плагин: `NearestQuestTracker.esp` (ESL-flagged).
Нативный плагин: `NearestQuestTracker.dll`. MCM: `Data\MCM\Config\NearestQuestTracker\`.
Раскладка проекта как у остальных модов: `papyrus/`, `tools/` (gen_esp.py, gen_mcm.py,
deploy.py, package.py — взять за основу из `fo4-free-sprint-out-of-combat`), `build/`,
`release/`, `f4se_plugin/`, README.md + README.ru.md, LICENSE (Unlicense).

## Порядок тестирования (решение пользователя 2026-09-30)

В каждом этапе — только **минимальный тест** в игре: одна проверка, что новая функция вообще
работает. Всё остальное считаем рабочим и дописываем сценарий в «Чеклист полевого теста».
Когда мод будет готов, пользователь сам играет с ним «в боевых условиях» и отмечает по чеклисту,
что работает, а что нет; тогда чиним по его отчёту. Лишних запусков и перезапусков игры не делать.

## Решения и находки

- Pip-Boy SWF **не редактируем**: весь интерфейс через хоткеи, MCM и уведомления.
- В ванильном `Quest.psc` есть `SetActive(bool)`, `IsActive()`, `IsRunning()`,
  `IsCompleted()`, `IsObjectiveDisplayed/Completed()` (проверено по исходнику 2026-09-30).
  Функций для перечисления квестов Pip-Boy и позиций их целей в Papyrus **нет**,
  поэтому нужен F4SE-плагин.
- «Отметить квест» = `Quest.SetActive(true)` (галочка отслеживания в Pip-Boy).
  Квест, уже стоящий в списке Pip-Boy, только отмечается. Остальные квесты
  получают `SetActive(false)`, если включена настройка «Снимать отметку с остальных»
  (по умолчанию ВКЛ). Исключённые квесты тоже теряют отметку: исключение значит
  «не веди меня туда».
- **Требование пользователя (2026-09-30):** работа хоткея «Отметить ближайший квест»
  зависит от настройки MCM **«Отмечать не начатые квесты»**:
  - ВЫКЛ: кандидаты только квесты из списка Pip-Boy (как в этапе 1).
  - ВКЛ: кандидаты = квесты Pip-Boy + точки старта не начатых квестов (данные 3a).
    Побеждает ближайший из всех. Если это не начатый квест, ставится маркер старта
    (механизм 3b) вместо `SetActive`. «Снимать отметку с остальных» действует так же;
    прежний маркер старта при этом снимается.
  - По умолчанию **ВЫКЛ** (решение пользователя 2026-09-30).
  - Сама настройка появляется в 3b, потому что до этапа 3 данных о стартах нет. В 1b/1c
    `FindNearestQuest` проектировать так, чтобы в него можно было добавить второй
    источник кандидатов (общая функция расстояния и общий тип «кандидат»).
- (сюда дописывать находки: адреса/функции движка, раскладки структур, ограничения MCM…)

### Как движок хранит цели квестов (OG 1.10.163, проверено дизассемблером)
- `PlayerCharacter`: `questTargetLock` BSSpinLock +0x630; `objectives`
  BSTArray<BGSInstancedQuestObjective> +0x7D8 (size +0x7E8); `questTargets`
  BSTHashMap<TESQuest*, QuestTargetArray*> +0x7F0 (capacity +0x7FC, entries +0x818,
  запись 0x18: key, value, next). CommonLibF4 объявляет то же. Обходить под
  `questTargetLock`, как делает движок.
- `QuestTargetArray` = BSTArray<X*> (data +0, size +0x10); у каждого X по +0x20 лежит
  BSTArray<REF_DATA*> (data +0x20, size +0x30). X, вероятно, TESQuestTarget;
  **уточнить в 1b**.
- `TESQuestTarget::REF_DATA` (ctor rva 5FC8D0): +0x00 `TeleportPath`
  (0x50 байт), +0x50 ObjectRefHandle цели, +0x58 отложенный запрос пути, +0x60 bool.
- **Готовое расстояние с учётом дверей:** `TeleportPath::ComputeLength()` (id 95565)
  для `REF_DATA` = длина пути игрок → цель через двери. `REF_DATA::GetTrackingRef()`
  (id 1490112) возвращает handle ref для маркера: дверь, если цель в другой ячейке.
- В движке уже есть `FindNearestObjective(ClosestQuestTarget&)` (id 1411385): обходит
  `questTargets` под локом и берёт минимум `ComputeLength` по всем REF_DATA, но **только
  у квестов с `TESQuest::GetActive()`** (id 690102). Вызывает его только `GuideEffect`
  (архетип эффекта «проводник»). **План 1b:** повторить этот функтор без фильтра GetActive.
  Свой обход интерьеров и дверей, скорее всего, не нужен.
- Пути строит `TESQuestTarget::UpdateTargetArray` (id 1396355) →
  `DeferredBuildPathToTarget` асинхронно. Проверки GetActive в этой цепочке нет,
  значит пути, вероятно, есть и у неотмеченных квестов. **Проверить логом в 1b**
  (квест без отметки: REF_DATA есть, ComputeLength > 0). Запасной вариант:
  `TESObjectREFR::BuildPathToTarget(target, TeleportPath*, bool, bool)` (id 1340025) или
  `PlayerCharacter::GetTotalDistanceToTarget(ref)` (id 1514377).
- `TESQuest::SetActive(bool)` id 1567562. ID выше указаны для OG. NG-ID для 1b/3c брать
  из CommonLibF4 (RelocationID), а где их нет, искать отдельно.

### 3d: сделано (2026-10-01) — квесты без маркера и порядок по мирам

  половина квестов Содружества тоже «в Ядер-Мире». Две ошибки: (1) в запасном проходе по дверям брался мир, где дверь
  **стоит** (дверь транзита в Ядер-Мире), а не куда ведёт — теперь выход хопа = следующая дверь или связанная дверь
  (ExtraTeleport); (2) выгруженные persistent-ref'ы лежат в persistent-ячейке мира (`TESWorldSpace::persistentCell` +0x70,
  FormID 0, флаг formFlags бит 10, `TESWorldSpace::CreatePersistentCell` rva 495A10), и её поле `worldSpace` дало Ядер-Мир
  для ref'ов Содружества (гипотеза, проверяется дампом) — `WorldOfCell` ищет мир по указателю persistentCell. Тем же
  исправлены `CollectWorldEntries` и `MeasureStraight`. В дампе у наружных ref'ов теперь `world … (persistent cell …, field …)`.
- **Тест 2: провал, но дамп всё объяснил:** у выгруженных persistent-ref'ов (двери транзита/пещеры, цель Сэнкчуари)
  **`GetParentCell()` = null** («cell 00000000» в дампе — это null). Мир находился только у первой двери пути (она в мире
  рынка 06053C58 → корень Ядер-Мир). Движок в `TESObjectREFR::GetWorldSpace` (rva 40F290) для null-ячейки зовёт
  `GetSaveParentCell` (vfunc 0xBE: для persistent-ref'а — `ExtraPersistentCell`, persistent-ячейка его мира). Теперь
  `CellOf(ref)` = parentCell или GetSaveParentCell; обратный проход по дверям останавливается на двери в интерьере
  (дальше — другой мир), тогда — мир плагина.
- **Тест 3 (2026-10-01): ОК.** Все квесты Содружества — мир 0000003C, Фар-Харбора — 03000B0F; ранг 0 только у двух

- **Но:** «Путешествие к звездам» пользователь завершил консолью — квест completed, а цель 905 осталась в состоянии 1
  (показана). Pip-Boy его не показывает, `SetActive` ничего не дал, остальные отметки сняты — в Pip-Boy пусто. Pip-Boy
  (`IsValidForJournal`) статус квеста не проверяет, но кнопка отметки (`ToggleQuestActiveStatus`) требует running && !completed.
  Теперь `Engine::IsQuestTrackable` (flags & 3 == 1) фильтрует квесты в `DisplayedQuestsLocked` и `GetObjectiveSignature` —
  касается и квестов с маркером. **Тест 4 (2026-10-01): ОК** — отмечены «Драгоценные медальоны» (без маркера), в Pip-Boy
  отмечены. В игре снова **Release-DLL**.
- Собрано, разложено в игру (Release-DLL). Минимальный тест — у пользователя (см. чеклист 3d).

## Этап 1 — ближайший квест из Pip-Boy по хоткею

Итог этапа: нажатие хоткея отмечает квест с ближайшей целью, остальные теряют
отметку (если включена настройка). Появляется уведомление «Отслеживается: <название квеста>».

### 1a. Исследование и сборочный стек (отдельная сессия)
1. Выбрать стек: CommonLibF4 (+ xmake/CMake) или классический F4SE SDK 0.6.23.
   Игра пользователя: **1.10.163**, F4SE 0.6.23. Целимся в неё; для NG/AE (1.10.984 /
   1.11.x) закладываем Address Library и собираем отдельную DLL позже (этап 3c).
   Проверить, что уже стоит: VS/MSVC, xmake/cmake, vcpkg; есть ли CommonLibF4 у LootMan 3.x.
2. Найти в CommonLibF4 / дизассемблировать (правило: проверять на бинарнике, а не по
   комментариям):
   - список целей игрока, который показывает Pip-Boy (`PlayerCharacter::objectives`,
     `BGSInstancedQuestObjective` → `BGSQuestObjective` → квест, индекс, состояние displayed/completed);
   - цели objective (`TESQuestTarget`: индекс алиаса + условия) → заполненный
     `BGSRefAlias` → `TESObjectREFR`; для location-алиасов маркер карты локации;
   - функцию движка, которая считает позицию маркера компаса/карты для цели в интерьере
     (дверь наружу). Если не найдётся, писать свой обход: ячейка интерьера → двери с
     teleport → внешняя дверь (с ограничением глубины).
3. Записать находки в «Решения и находки». Собрать пустой плагин, который грузится и
   пишет строку в `NearestQuestTracker.log`: так проверяется весь стек.

### 1b. Нативный поиск (отдельная сессия)
Papyrus-функции (скрипт `NQT_Native.psc`, native global):
- `Quest[] GetTrackedQuestList()`: квесты с хотя бы одной displayed и не completed целью.
- `Quest FindNearestQuest(FormList akExcluded)`: ближайший квест не из списка исключений.
- `float GetQuestDistance(Quest akQuest)`: для отладки и уведомлений (-1, если цели нет).

Алгоритм расстояния:
- Позиция игрока: если он в интерьере, берётся его «внешняя» точка (дверь наружу из
  текущей ячейки) и worldspace этой двери.
- Позиция цели: ref во внешнем мире берётся как есть; ref в интерьере заменяется
  внешней дверью (см. 1a); у цели с несколькими targets берётся ближайший.
- Расстояние в 2D (X/Y) внутри одного worldspace. Цель в том же интерьере, что и игрок,
  даёт расстояние 0. Другой worldspace (Фар-Харбор, Нюка-Мир, Институт…) получает
  большой штраф: выбирается только если в текущем мире целей нет.
- Цели без позиции (пустой алиас, не выполнены условия target) пропускаются. Квест
  без единой позиционной цели в поиске не участвует.
- Лог в Debug-сборке: каждый квест, его цели, позиции, итоговое расстояние.

### 1c. ESP + Papyrus + MCM (отдельная сессия)
- `tools/gen_esp.py`: квест `NQT_MainQuest` (start game enabled) со скриптом
  `NQT_MainScript`, FormList `NQT_ExcludedList` (пустой), GLOB-настройки.
- `NQT_MainScript.TrackNearest()`: `FindNearestQuest`, затем `SetActive(true)` у найденного;
  при `bUntrackOthers` `SetActive(false)` у всех остальных из `GetTrackedQuestList`.
  Уведомление с названием (F4SE `GetName`). Если квест не найден, уведомление
  «Нет квестов с маркером поблизости».
- MCM: хоткей «Отметить ближайший квест», переключатель «Снимать отметку с остальных»,
  переключатель уведомлений.
- Строки en/ru: как в AutoMedic 1.3.0 (выбор по `sLanguage`).

### 1d. Тест в игре (отдельная сессия, с пользователем)
Сценарии: несколько квестов в Содружестве; игрок в интерьере; цель в интерьере;
квест в Фар-Харборе при игроке в Содружестве; квест без маркера; «Снимать отметку» ВЫКЛ.
Проверить, что после перезагрузки сохранения отметки остаются и лог чистый.

## Этап 2 — исключения и настройки

### 2a. Исключения (отдельная сессия)
- Хранение: `NQT_ExcludedList.AddForm/RemoveAddedForm`, список сохраняется в сейве.
- Хоткей «Исключить квест»: исключает квест, который мод отметил последним; если его
  нет, берётся ближайший из отмеченных. Уведомление «Исключён: X». Сразу после этого
  ищется и отмечается следующий ближайший квест.
- Хоткей «Вернуть последний исключённый» (стек/отмена).
- Завершённый или остановленный квест автоматически убирается из исключений (чистка
  при загрузке сейва и при каждом поиске).

### 2b. MCM: список исключённых (отдельная сессия)
- Сначала проверить на реальных конфигах установленных модов (`Data\MCM\Config\*`)
  и документации MCM, умеет ли MCM динамический текст или выпадающий список из
  строк скрипта. Проверять, не полагаясь на память.
- Вариант A (если динамика есть): список исключённых с кнопкой «Вернуть» у каждого.
- Вариант B (запасной): слайдер «№ исключённого квеста», текст с его названием
  (через `SetModSettingString`), кнопка «Вернуть этот»; плюс кнопка «Вернуть все».
- Там же: «Снимать отметку с остальных», уведомления, все хоткеи.

### 2c. Автопересчёт + тест (отдельная сессия)
- Опция «Автоматически»: пересчёт, когда у отмеченного квеста выполнена цель
  (событие objective/stage через F4SE-sink в нативном плагине или опрос по таймеру
  раз в N секунд; выбрать по результатам 1a) и когда начат новый квест.
  По умолчанию ВЫКЛ.
- Минимальный тест автопересчёта; сценарии хоткеев, MCM, сохранения/загрузки, чистки исключений —
  в «Чеклист полевого теста».

## Этап 3 — маркер ближайшего неначатого квеста + релиз

### 3a. Данные: точки старта (отдельная сессия)
- Файл `Data\F4SE\Plugins\NearestQuestTracker\QuestStarts.json` плюс опциональный
  `QuestStarts-user.json` для пользователя (формат как `items-user.json` у AutoMedic).
  Запись: плагин + FormID квеста, плагин + FormID ref (NPC/активатор/дверь),
  опционально стадия, при которой старт считается уже пройденным.
- Сбор данных полуавтоматический через `tools/esm.py` по Fallout4.esm + DLC:
  квесты с диалогами игрока, где условия `GetStage < N` стоят на конкретном NPC
  (квестодатель); затем ручная проверка по вики (fandom: список квестов/квестодателей).
  Radiant-квесты, квесты из записок/радио/Story Manager и основной сюжет после
  старта не включать. Ожидается ~100–150 записей.
- Не класть в репозиторий ванильные файлы, только наш JSON с FormID.

### 3b. Маркер (отдельная сессия)
- Натив: `ObjectReference FindNearestQuestStart()`. Кандидат: квест не запущен и не
  завершён (или стадия < указанной), ref включён, NPC жив, тот же worldspace
  (расстояние как в 1b).
- ESP: квест `NQT_StartMarkerQuest` с optional-алиасом `StartRef` и objective
  «Начало нового квеста: <Alias=StartRef>»; второй objective без имени для режима
  «без спойлеров». Техника та же, что в Nuka-Cola Recipe Markers / SCCM:
  `ForceRefTo` + `SetObjectiveDisplayed`.
- Пересчёт по хоткею «Показать ближайший новый квест» и (опционально) при смене
  локации. Маркер снимается, когда квест начат или игрок в радиусе N метров
  поговорил с NPC. MCM: вкл/выкл, «без спойлеров», хоткей.
- Настройка «Отмечать не начатые квесты» для основного хоткея «Отметить ближайший
  квест» (см. «Решения и находки»): при ВКЛ `FindNearestQuest` сравнивает квесты
  Pip-Boy и точки старта вместе; победил старт → маркер старта, а не `SetActive`.

### 3c. Тест + релиз (отдельная сессия)
- Минимальный тест маркера старта; дальше пользователь играет с готовым модом и отмечает
  «Чеклист полевого теста», чиним по его отчёту до релиза.
- Сборка DLL для NG/AE (Address Library), если на этапе 1a выбран мультиверсионный
  стек; иначе явно указать в описании поддерживаемую версию.

- Nexus: страница, требования (F4SE, MCM, Address Library), теги, картинки; блок
