# Nearest Quest Tracker (NQT) — план 2.0: локации и своё окно

Работа идёт в отдельных сессиях, по одному этапу или подэтапу за сессию.
**В начале каждой сессии:** прочитать этот файл (раздел «Статус» и нужный этап), затем
`..\FALLOUT4_MOD_DEVELOPMENT_GUIDE.md` (разделы 1 и 2). Находки по движку, сборочный стек,
устройство хоткеев/маркеров/данных стартов — в **`PLAN-1.0.md`** («Решения и находки», «…: сделано»);
читать нужный раздел оттуда, а не выводить заново.
**В конце сессии:** обновить «Статус» и «Решения и находки», дописать сценарии новой функции
в «Чеклист полевого теста».

План 1.0 (`PLAN-1.0.md`) закрыт 2026-10-04: пользователь проверил мод в игре, основные функции
работают. Мелкие баги чиним отдельно по мере обнаружения (раздел «Баги»), не дожидаясь этапов.

Префикс, файлы, раскладка проекта — как в 1.0: `NQT`, `NearestQuestTracker.esp` (ESL),
`NearestQuestTracker.dll`, MCM `Data\MCM\Config\NearestQuestTracker\`, папки `papyrus/`, `tools/`,
`f4se_plugin/`, `mod/`. Новое: исходники окна — `menu/` (AS3), готовый SWF — `mod/Interface/NearestQuestTracker.swf`.

## Баги

Найденные пользователем мелкие баги: что, где, статус. Каждый чинится отдельной небольшой сессией.

- 2026-10-07: после загрузки сейва маркер локации в Pip-Boy («Разное») подписан «Location» (текст ESP), а не «Локация: …».
  Причина: Pip-Boy (`PipboyQuestData`) хранит свою копию текста цели, сделанную при загрузке — до `OnPlayerLoadGame`, где
  скрипт ставит текст; на маркере старта то же. Исправлено: `SetObjectiveText` после замены текста шлёт
  `PlayerCharacterQuestEvent::Notify(1 = цель обновлена, &player->objectives[i])` (OG id 395737) под `questTargetLock` —
  как `PlayerCharacter::UpdateInstancedQuestObjective` (rva EA4240); Pip-Boy по нему делает `UpdateObjective` →
  `GetDisplayText`. Без повторного показа цели (нет всплывашки на HUD). **Проверено пользователем 2026-10-08: исправлено.**
- 2026-10-11: `MS05MiscSalem` (цель «Разное» — Сейлем для `MS05B` «Роковые яйца») без категории: правило указателей
  берёт родителя по префиксу editor ID, а `MS05B` — не префикс. Проверены все квесты мастеров с целями без категории;

### 1c: находки (2026-10-04, OG 1.10.163, дизассемблер)
- **Туман войны интерьера** — в `ExtraSeenData` ячейки (тип extra 5, `SeenData*` на +0x18; `ExtraDataList::GetSeenData`
  rva 94600). Для интерьера (cellFlags +0x40 бит 0) это цепочка `IntSeenData` (ctor rva D57110, 0x38 байт): vtable,
  16×16 бит на +0x08 (индекс y·16+x, `SeenData::IsSeenBitTrue` rva D56BC0), координаты секции `x`,`y` (s8) на +0x28/+0x29,
  следующая секция на +0x30. Секция = квадрат 4096×4096 ячейки (`(pos − 0x800) >> 12`), бит = квадрат 256×256;
  `TESObjectCELL::GetIntSeenSection` (rva 3C19D0) создаёт секции по мере надобности. Бит ставит
  `SeenData::UpdateSeenData` (rva D56CD0) — центр квадрата ближе радиуса (глобал, вероятно `fSeenDataUpdateRadius`).
- **Кто пишет:** обновление игрока (`PlayerCharacter`, rva E9DFA3) каждый кадр зовёт
  `TESObjectCELL::UpdateSeenDataForPlayerLoc` (rva 3C10F0) для своей ячейки, **без условий** — значит, SeenData появляется
  у любого интерьера, где игрок постоял, и с картой, и без. Экстерьер: один `SeenData` на ячейку, а когда открыт весь, он
  удаляется и ставится `cellGameFlags` (+0x42) бит 0.
- **Сейв:** `TESObjectCELL::SaveGame` (rva 3C0A00) пишет SeenData под флагом изменения **0x80000000** (`kCellSeenData`),
  `LoadGame`/`Revert` восстанавливают/сбрасывают. `TESObjectCELL::ClearSeenData` (rva 3C10B0) прямых вызовов не имеет.
  Сброс ячейки (`CheckShouldReset`, `HandleExpiredReferences`) работает с ref'ами, SeenData не трогает (по коду; проверить).
- Натив `NQT_Native.DumpInteriors` (`Interiors.h/.cpp`: `GetInteriorSeen`): число интерьеров с SeenData, секции/биты каждого;

  не загружена), 60 ближайших дверей с туманом их интерьеров. Консоль: `cgf "NQT_Native.DumpInteriors"`.

  - сразу после загрузки сейва SeenData есть у 91 из 1414 интерьеров (изменения ячеек применяются при загрузке сейва, сама

### 3b: сделано (2026-10-11, минимальный тест ОК)
